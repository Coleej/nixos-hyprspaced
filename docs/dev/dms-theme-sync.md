## How DMS drives theming

One place changes light/dark. On a theme switch DMS:

1. Writes `org.gnome.desktop.interface color-scheme` via gsettings
   (`Services/PortalService.qml` `setSystemColorScheme`). Light mode writes `'default'`,
   not `'prefer-light'` (see "Findings worth remembering").
2. Sets the GTK theme name via `Common/Theme.qml` `refreshGtkTheme`.
3. Re-runs matugen, regenerating per-app files: `~/.config/gtk-3.0/dank-colors.css`,
   `~/.config/DankMaterialShell/firefox.css`, `~/.config/nvim/colors/dms.lua`,
   `~/.config/alacritty/dank-theme.toml`, and others.

`syncModeWithPortal` defaults to `true`. The DMS shell sources live in the store under
`share/quickshell/dms/` of the `dms-shell` package (`scripts/gtk.sh`, `Common/Theme.qml`,
`Common/SettingsData.qml`, `matugen/configs/*.toml`).

## What was wrong, per app

### Evolution

Home Manager was pinning every key DMS owns: `color-scheme = "prefer-dark"`,
`gtk-application-prefer-dark-theme = true`, and `gtk.theme = Adwaita-dark`. DMS writes the
first and the gtk-theme key itself, so HM re-asserting them on every activation made the
desktop fight itself (upstream `AvengeMedia/DankMaterialShell#2786`).

Fix, in `modules/home/desktop.nix` (dankshell branch only): `gtk.theme = null`,
`gtk.colorScheme = null`, and the theme name pinned via `gtk3.extraConfig.gtk-theme-name =
"adw-gtk3"`. `gtk3.extraConfig` is the only input HM merges into `settings.ini` without also
writing dconf, which is why it is the right seam. GTK3 reads its theme name from
`~/.config/gtk-3.0/settings.ini` only, never from gsettings. `pkgs.adw-gtk3` is installed in
`modules/home/dankshell.nix`.

How the colours then arrive: `gtk.sh` copies `adw-gtk3` and `adw-gtk3-dark` into
`~/.local/share/themes` and appends a `/* BEGIN DMS OVERRIDE */` block of `@define-color`
rules. It patches per mode: light fills `adw-gtk3/gtk.css`, dark fills
`adw-gtk3/gtk-dark.css`. Because HM leaves `gtk-application-prefer-dark-theme` unset, GTK
3.24.22+ picks `gtk-dark.css` from the portal, so one static name covers both modes. The name
must stay `adw-gtk3`; `adw-gtk3-dark` would break light mode.

### Neovim

`matugenTemplateNeovim` defaults to `false` (`SettingsData.qml`), so
`colors/dms.lua` and the lualine theme were never generated. Separately, `init.lua`
hardcoded `tokyonight-night`. The generated `dms.lua` is a base46 colourscheme and needs the
`AvengeMedia/base46` plugin.

Fix: enabled the toggle (`dms ipc call settings set matugenTemplateNeovim true`, so it is
per-machine state, not Nix), swapped the plugin to `AvengeMedia/base46`, and load `dms`, with
a `tokyonight-night` fallback if the file has not been generated yet. The two generated
files are gitignored in the nvim repo. Measured: dark `Normal` bg `#101820`, light `#f7f9ff`.

### Firefox

Layered, and mostly not what it first looked like:

1. The Material Fox theme was not installed and there was no profile at the path the DMS
   docs give. **The DMS docs say `~/.mozilla/firefox`; Firefox 158 here uses
   `~/.config/mozilla/firefox/`.** Following the docs would theme nothing.
2. `firefox.css` generated by DMS is a drop-in for Material Fox's `theme-material-blue.css`
   (same `--md-sys-color-*` contract) and carries a light block plus an
   `@media (prefers-color-scheme: dark)` block. It is symlinked into the profile's `chrome/`.
3. **An active WebExtension theme (`firefox-compact-dark`) pins `prefers-color-scheme`** and
   overrides `widget.systemUsesDarkTheme` entirely. That is why every pref experiment did
   nothing for a long time.
4. **`extensions.json` is authoritative over the `extensions.activeThemeID` pref.** Setting
   only the pref does nothing.
5. **A stored session re-applies whichever theme was active when it was written**, so
   clearing the theme state without also clearing `sessionstore-backups/` reverted it.

Shipped in `configs/firefox/user.js`, installed by the `installFirefoxMaterialFox` activation
hook in `modules/home/dankshell.nix`: the three Material Fox prefs,
`extensions.activeThemeID = default-theme@mozilla.org`, and crash-session restore disabled.

## Mistakes made, and what they cost

Recorded plainly so they are not repeated.

- **Deleted Firefox's `prefs.js` to clear stale theme state. This broke every extension.**
  `prefs.js` holds `extensions.webextensions.uuids`, the only map from extension ID to the
  `storage/default/moz-extension+++<uuid>` directory holding its data. Without it Firefox
  mints fresh UUIDs on the next start and orphans all storage. All 8 extensions kept
  reporting `active=true` in `about:addons` while having lost settings, tokens and logins,
  so it looked healthy. Recovered by pairing each extension ID with the UUID of an existing
  storage dir, using the map from an earlier dump. **Never delete `prefs.js` on a profile
  with extensions or Sync.**
- **The activation script used `awk`, which is not on the activation PATH.** It exited 127,
  took `home-manager-cody.service` down and failed `nixos-rebuild` with status 4. The user's
  screenshot caught it, not my testing. Rewritten in bash builtins.
- **Bash `${line#Path=}` inside a Nix indented string is a hard eval error** (interpolation).
  It must be written `''${line#Path=}`. Confirmed by evaluating the string through Nix.
- **x1's extension UUID map was hardcoded in the file installed on every host.** On another
  machine it would have pointed that host's extensions at non-existent storage, the same
  failure as the `prefs.js` deletion but delivered by Home Manager. Removed; the hook now
  preserves whatever map the destination profile already has.
- **The runbook's profile-resolution `awk` was wrong.** `Default=1` comes *after* `Path=` in
  a `profiles.ini` block, so the first draft never matched and resolved to an empty string.
  `[ -d "$PROFILE" ]` still passed (it was just the parent directory), so `unzip` would have
  extracted into the wrong place. Found only by running the snippet extracted from the
  markdown.
- **I said "Evolution looks good" before any rebuild had succeeded.** That was the old
  `Adwaita-dark` config, which looks fine for unrelated reasons, so it was no evidence at all.
- **I tried the global `@import dank-colors.css` route and had to back it out.** It cannot
  coexist with `adw-gtk3`: `gtk.sh apply` calls `ensure_user_adw_gtk3` first and re-copies the
  theme from `XDG_DATA_DIRS` every run, and any later "Apply GTK Colors" deletes the import.
- **I concluded `gtk.css` was unpatched because I grepped for `--md-sys-color-*`.** DMS injects
  `@define-color` rules, not CSS custom properties. In dark mode it patches `gtk-dark.css`
  and deliberately leaves `gtk.css` alone.
- **My Firefox tests were unreliable for a long time**, for two separate reasons below.

## Debugging environment: hazards

- **`pkill -x firefox` is a silent no-op.** The NixOS wrapper renames the process to
  `.firefox-wrappe`. Every "restart" for the first several tests reused the same live
  instance, so those results were meaningless. Use `pkill -9 -x '.firefox-wrappe'` and check
  with `ps -eo comm | grep -c '^\.firefox-wrappe'`. SIGTERM is not a clean quit for Gecko; it
  leaves a recovery session and `about:sessionrestore`.
- **`firefox --screenshot` produced byte-identical PNGs** across different prefs, profiles
  and windowed vs headless. Do not use it as a probe. Use `grim <file>` on the real window.
- **The test page only tells the truth at startup.** `/tmp/opencode/scheme.html` evaluates
  `matchMedia('(prefers-color-scheme: dark)')` once at load. After a live toggle it still
  shows the old answer. For live behaviour, look at the browser **chrome** (tab strip,
  toolbar), not the page. I misread this at least once.
- **`hyprctl dispatch` is broken** under this Lua-based Hyprland config ("dispatch in lua is a
  shorthand for hl.dispatch(...)"), and there is no `hl` binary. `hyprctl clients -j` works.
  Consequence: no way to raise or focus a window, so a GTK3 window can only be seen if it
  happens to be on top in a `grim` capture.
- **Home Manager activation has a minimal PATH**: no `awk`, `grep` or `sed`. Use bash
  builtins plus coreutils.
- `dms ipc call theme toggle|getMode`, `dms ipc call settings get|set <key> <value>` all work.

## Open problem: Firefox does not follow DMS

### What is established

- The portal does reflect DMS. `org.freedesktop.appearance color-scheme` reads `0` after
  DMS writes `'default'` (light) and `1` in dark. With `'prefer-light'` it reads `2`.
  DMS writes `'default'` rather than `'prefer-light'` in light mode, and `0` means "no
  preference", so a client that treats `0` as dark would see dark in light mode.
- **A brand-new profile with no prefs rendered LIGHT while DMS was light.** The real profile
  rendered DARK in the same conditions. So Firefox's system detection can work here, and
  something in the real profile breaks it.
- **It worked once, for a while.** After deleting `prefs.js` (see mistakes) and restarting,
  Firefox came up light with DMS light, with no hardcoded scheme pref, and the chrome
  followed two toggles in the same running instance. The next session should treat "what
  was different about that state" as the key question.
- Later it regressed. After the rebuild, `extensions.json` had **inverted again**:
  `default-theme@mozilla.org active=False` and `firefox-compact-dark@mozilla.org
  active=True`, even though `prefs.js` and the shipped `user.js` both said
  `default-theme`. Re-applying it fixed the theme state and it survived a restart, but
  Firefox then still started dark in light mode.

### Tried at the end, none changed the startup result

| Attempt | Result |
| --- | --- |
| `extensions.activeThemeID = default-theme` plus `extensions.json` corrected | Starts dark |
| `extensions.systemTheme.update.enabled = false` | Starts dark (pref name unverified for this build) |
| `dconf color-scheme = 'prefer-light'` (portal reported `2`) | Starts dark |
| `widget.systemUsesDarkTheme = 1` | Starts dark |

All of these were reverted. The repo file is back to its committed state, and the profile's
`user.js` was reinstalled from it.

### Leading hypothesis, never tested: Firefox Sync

This is the lead I did not follow up. It is **a hypothesis, not a finding.**

- The profile has an active Sync directory (`weave/`), and `prefs.js` carries
  `services.sync.prefs.sync-seen.extensions.activeThemeID = true`, which means the active
  theme is a synced pref.
- `weave/addonsreconciler.json` was being rewritten during the session (20:22 on the day
  of the work), and `weave/failed`/`toFetch` were churning.
- `extensions.json` flipping back to `firefox-compact-dark` after being corrected, with no
  local action that would do it, fits Sync re-applying a theme from another device.
- Deleting `prefs.js` would have reset the `sync-seen` state, which might explain why it
  worked right after that deletion and regressed later.

Test it before building anything: with Firefox closed, correct `extensions.json`, then in
`about:preferences#sync` turn off syncing of **Add-ons** and **Settings** (or sign out of
Sync), restart, and see whether the theme stays. Also compare `extensions.json` mtime against
the Sync activity timestamps.
